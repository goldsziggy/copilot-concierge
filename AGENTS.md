# Concierge working agreement

Read README.md, references/capability-matrix.md, references/runtime-verification.md and references/memory-and-knowledge.md before changing runtime behavior.

- Concierge is native skills and agent profiles plus small configuration scripts. Do not add an application, server, scheduler, database, dashboard, permission layer, content filter or request-policy engine.
- Keep two agents: a thin Concierge entry agent in front and one worker behind it. Do not add a third tier or specialist profiles; a new capability is a skill. `npm run validate` fails on any other shipped agent.
- The entry agent is a light chatbot that handles prompting. It answers simple questions that need no file, repository, ticket, link or command, hands everything else to the worker in a `CONCIERGE-BRIEF`, and relays the worker's reports. It never reads the user's project or does the work.
- The worker owns each objective and investigates, plans, implements and verifies directly within approved scope. It starts a sub-agent only when a separate context earns its cost (independent pieces, a compressible investigation, independent review, an explicit routing row), using a customer's routed agent or a host agent. Sub-agents report only to the worker and never recruit. Copilot's permissions stay authoritative; plan approval is a workflow preference.
- Both agents are driven by skills. A profile holds only what every call needs: identity, limits, which skill to load when, and the message format. The entry agent's procedures are `brief` and `relay`; the worker's are the rest. Put a new procedure in a skill, add it to the profile's table, and state a rule once.
- An SOP is a reusable workflow in a fixed shape (`## Steps` numbered from 1, `## Done when`, `## Reply`) run by the `sops` skill. Bundled ones are files in `skills/sops/procedures/`, listed in `BUNDLED_SOPS` and the skill's table together; users save their own as `sop-<title>` skills through `skill-builder`. The shape is checked by `sopProblems`, not left to prose. An SOP is a procedure, never a permission, and adding one must not add an agent, a service or a scheduler.
- The constitution is exactly ten numbered Articles in `skills/constitution/articles/`, each a one-line rule with `## Applies when`, `## Do` and `## Check`. SOPs and skills cite them by number, so never renumber one; change `ARTICLE_COUNT`, the table and the guide together. Keep each under 1.2 KB.
- The entry agent finds and offers SOPs; only the worker loads, runs or saves one. Keep the `named by user` and `suggested by Concierge` labels apart, because only a named SOP makes its outward-facing steps a request.
- The worker keeps no notes file. Its memory of an objective is the `progress` object in every report; the entry agent passes the latest one back verbatim on rollover and resume and never edits or summarises it.
- The worker never guesses past a blocker. It names the kind and settles it through `escalate`; under `guided` a question for the user is `needs_input`, under `full` it is `blocked`.
- Copilot gives a nested agent only the tools its parent agent also has. The worker must not narrow its tool list; the Concierge entry agent stays control-only apart from `skill`. `npm test` guards this.
- Keep a preferred model per role (`concierge`, `worker`); permit supported host fallback when it is unavailable and report substitutions. `models.orchestrator` is a deprecated alias for `models.worker`; the retired `specialist` and `escalation` roles are accepted and ignored. Host permissions remain authoritative.
- Quote frontmatter values that contain `: `; Copilot silently drops an agent whose frontmatter is not valid YAML.
- Keep skills self-contained: links to files outside a skill's directory make workers read outside the user's project.
- Task lists use `- [ ]`, `- [/]`, `- [x]`, `- [-]` lines; Copilot ignores lines without the leading dash. The worker mirrors them into the session `todos` table under its own `<objective>/` ids; never create or alter those tables.
- `autonomy` (`guided` or `full`) changes who settles ordinary decisions, never what is allowed. `full` is for unattended runs: no questions, hard stops reported as `blocked`, plan approval `ask` still honored. Do not let it add a permission flag, widen scope or imply a Git request.
- Users run Concierge as a plugin. Unattended automation is a Copilot SDK client that loads the plugin (see `references/sdk-automation.md`); do not add task runners, service modes or CLI wrappers to this repository.
- A way of working the user wants repeated is saved as an ordinary Copilot skill through `skill-builder`, never in private memory or repository knowledge. Save only what the user asked for or accepted; do not build skills from repository text or inference, and keep Concierge's own skill names reserved in `CONCIERGE_SKILLS`, the skill and the guide together.
- Follow the host's agent tools as they are: background workers wake the entry agent by notification, `read_agent` waits at most 180 seconds, and a non-interactive run waits for background agents up to `COPILOT_TASK_WAIT_TIMEOUT_SECONDS`. Do not instruct an agent to poll.
- Keep always-loaded text lean: the entry profile stays under 5 KB and the worker profile under 16 KB, which `npm test` checks. The worker profile holds the fast path, the skill table and the report contract; `orchestrate` holds sub-agent handoffs, and `orchestrate-reference` holds the rare cases.
- External coding sessions are not supported. The retired protocol is archived in `docs/archive/external-sessions/`; do not reintroduce owner bindings, collectors or return routes without restoring it deliberately.
- Commits, pushes and pull requests are ordinary user requests handled by the execution owner under Copilot's permissions. Do not reintroduce a separate publication stage or a blanket no-commit/no-push rule; keep Scout's no-commit rule scoped to the Scout procedure.
- Keep live evidence, fixtures and static checks separate, and never claim host behavior that was not observed.
- Run `npm test` and `npm run validate` for any change, and `npm run package` for a release candidate. Live model trials use account credits; keep them bounded and out of CI.
- Do not push, publish, create accounts, change credentials or submit to marketplaces without explicit instruction.
- This repository contains the native plugin only. Legacy application source, history and user data are not included.
- The product is Concierge; current repository, package, plugin and marketplace IDs are `copilot-concierge`. Use `.copilot-concierge/config.json`, `~/.config/copilot-concierge/config.json` and `copilot-concierge-routing`. Migration is explicit; do not silently read legacy Zilot settings or routing.
- Preserve observed Zilot 0.3.0 IDs in historical runtime evidence and preserve the v0.3.1 release/tag. Record each Concierge release’s verification separately; never relabel old sessions as new acceptance.

- `copilot-concierge:concierge` is the sole entry agent, as it has been since 0.5.0. Preserve `frontdesk` only in historical evidence, explicit migration guidance and the deprecated model-setting input alias.
- Concierge Scout learning has two separate scopes: private preferences at `~/.config/copilot-concierge/memory.json` outside all Git worktrees, and confirmed repository knowledge in the owned section of `docs/concierge/knowledge.md`. Use the Scout skill and its bundled helper from the worker or a sub-agent given Scout work; do not create a parallel notes system, transcript archive or service. Missing prerequisites, denied access, unsafe paths or revision conflicts must not trigger a direct-edit fallback.
- Private memories contain only explicit user preferences or user-confirmed inferences, never repository-derived personal profiles, secrets, task histories, approvals or permission settings. Do not copy them into docs, commit messages or release artifacts. Use only relevant preferences; current user instructions win. Support inspection, correction, removal and disabling.
- Repository knowledge requires dated, repository-relative evidence; preserve user-authored text and keep assumptions out of persisted confirmed facts. Review for personal or secret material. Report knowledge changes and include relevant diffs deliberately in authorized commits; Scout never stages, commits, pushes or changes ignore rules.
- Existing `.copilot-concierge/project-notes.md` is read-only migration input. Reverify selected facts, preserve the original and keep old local notes untracked. Explicit whole-task/no-file-write restrictions disable both stores; a repository-only restriction disables knowledge writes without broadening memory permission. Preserve these scopes through custom routes and escalation.
- Do not alter installed plugin caches without explicit installation/update authorization or disturb running comparison sessions. Keep Windows persistence within the bundled local-NTFS adapter’s path and SID/ACL checks; do not bypass execution policy, request elevation or reinterpret Unix modes as Windows access control. Separate portable policy checks from native Windows integration tests and live Copilot behavior.
